# C的问题根因与修复实现

本轮以V4/Qwen0.6B五题BC全部部分答对的记录为基线。没有更换embedding、改写语料、调整参考答案或重建图谱。

## 根因证据

1. **预算计数过于保守。** 未配置分词器时，AnswerModel.count逐字节累加UTF-8长度。上一轮8088的TR04消息以o200k_base复算仅2353消息token；10份消息实际估算范围为1915～2439。所谓8192证据预算实际只装入约2300消息token。Codex响应中的总prompt用量含其他运行指令，不能拿来替代消息估算。见budget_audit.json。
2. **超窗复核被直接取消。** 旧代码压缩来源元数据后仍超窗便返回skipped_input_capacity，10份答卷中发生8次。证据组跨批次命名、缺项及配套关系因此没有完成最终复核。
3. **按长度收益优先偏向短聊天。** 旧pack_evidence以新增事项数/长度作主要选择依据，缺项目限定的短句经常胜过完整说明项目、环境、范围及分工的长文；候选覆盖18/19指定证据组，最终只保留B2组、C3组。
4. **事实被当作装满原文后的附加物。** C要求事实来源全文先入选，再把事实塞进剩余空间，既不能省原文预算，又重复占用空间。四题事实使用数为0，TR04的B/C最终输入完全一致。
5. **生成仍会漏掉必要推理条件。** PO03 C已有全部指定参考证据组，仍遗漏两个集合是否互斥未知。输入充分不自动保证回答完整。

## 实现

B/C共同采用明确的本地消息分词估算；32768上下文、8192证据和1800请求输出预算保持相同。全局复核支持已审核证据组索引卡及有界分窗，卡片只用于选择，最终回答仍以原文证据为依据。配套组不拆散，无法容纳时显式失败。选择优先级改为相关性、问题维度覆盖和语义重排顺序，成本退到可容纳性及平手处理。共同回答提示补充多对象覆盖、已有证据不要降为未知、集合口径与去重条件。

C另按精确溯源读取候选来源的提炼事实，利用事实类型和文本对应定位整句原文，在预算装入前构造可追溯节选。保留整句内的分号条件和相邻限定，不把抽象事实改写冒充原文；节选每段都有原始字符位置。原文全文仍在证据接口中，聊天不缩短。无法匹配、来源含糊或未节省空间时回退全文。离线检查128条记录从40393字符缩至7045字符，详见projection_audit.json。

这条路径让事实提炼承担“定位紧凑而有出处的业务证据”的作用；图谱仍补充关联来源与明确关系，二者作用分开记录。没有新增图节点/边类型，没有写入图谱。

## 验证与边界

24项相关测试通过（另有7个子测试），包括分窗不超容量、不丢来源、完整配套组、同预算下C节选可用、原文/否定/范围/位置保留以及缺失或错误来源回退。涉及A的2项测试未运行。默认五题的新答卷在eval-v4-c-repair-bc-2026-11-21目录生成，评测期间冻结代码和预算。

词语对应只是定位工具，不是语义蕴含证明；最终结论依据原文节选。事实抽取若漏掉关键内容或限定跨越较远段落，仍可能影响压缩完整性，因此需保留全文回查及语义评审。当前小规模Demo读取可见事实用于来源投影，大规模部署应改为按候选来源批量读取。分词估算不等于Codex服务端总上下文；编码可以显式配置。
