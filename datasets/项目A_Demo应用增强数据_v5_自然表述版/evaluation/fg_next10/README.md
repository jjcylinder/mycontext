## 如何评分

每题 3 个完整业务要点，全批共 30 个要点、66 个原子项。在最终输入上按模型实际可见的引文与关系计一次，在匿名答卷上按写出且有依据的判断再计一次。表中每条编号判断为一个原子项，计 0 或 1。一个完整要点内所有原子项都获分才计 1；整题 3 个要点均满足才算答全。编号和字段接受能唯一对应的业务表述。依据列中“＋”表示组合，“或”表示另一组可接受的材料。错连、错误放行、给出无依据结论另记；与错误断言冲突的判断不给分。

评分前只向两组提交 questions.jsonl 中的问题及运行参数；评分标准、证据 ID 和诊断线索仅供审核。先匿名评卷，再对照原文榜、事实榜、图谱榜、最终区间和路径。只有带进关键依据并改变可核实的业务判断，才能把相应题记为最终结果改善；同样记录 F 单独答对、G 挤掉直接材料和两组持平。共享实体线索已核实两端事实确实指向同一实体 ID，能否通过查询过滤并进入最终输入仍待实测。

FG09–10 两组均能做对，本题检查多条同名或同线程协作记录是否反而干扰直接答案。三项任务各自与正确角色匹配即可，不以找到额外路径加分。

| 完整业务要点与参考答案 | 原子评分项 | 可核对的原文 |
|---|---|---|
| 1. 对客场景由前方赵工确认。 | 1.1 场景确认归前方赵工 | `A01-S02` |
| 2. 消息和文档由数据吴工采集。 | 2.1 材料采集归数据吴工 | `A01-S02` |
| 3. 测试陈工负责范围及回归记录。 | 3.1 测试范围归测试陈工<br>3.2 回归记录归测试陈工 | `A01-S02` |

易误判之处包括把采集、场景确认或回归移交给其他角色。
